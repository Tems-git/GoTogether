# GoTogether

Семейни пътувания без главоболие.

## Стек

- React Native + Expo SDK 54
- Supabase (PostgreSQL + Auth + Storage + Realtime)
- Claude API (Anthropic) — AI Trip Planner, изпълняван през Supabase Edge Function (ключът не е в клиента)
- Resend — SMTP за OTP имейли (домейн: wegotogether.xyz)
- Frankfurter (ECB) — курсове за многовалутни разходи, прокси през Supabase Edge Function
- Expo Push + Firebase Cloud Messaging (FCM V1) — известия за нови съобщения в чата ✅ Android
- `react-native-safe-area-context` — реални safe area отстояния за iOS notch и Android navigation bar
- `expo-location` — координати за „Около мен" в планера; само на преден план, нищо не се пази
- `expo-share-intent` (5.1.1) — приложението се появява в списъка „Сподели с…" на Android
- `expo-media-library` + `expo-file-system` — записване на снимка от чата в галерията
- `expo-image-manipulator` — смаляване на снимките преди качване
- EAS Update — публикуване без App Store
- GitHub Actions — автоматичен EAS Update при push към master ✅ Работещ

## База данни — 11 таблици

profiles, trips, trip_members, trip_plans, expenses, expense_splits, documents, messages, removed_members, push_tokens, ai_usage

`messages.image_path` (от 2 септември) сочи снимка в кофата `documents`, в
подпапка `chat/` на съответното пътуване — същите правила за достъп, отделно
от Документите, които се изброяват от таблицата.

## ✅ GitHub Actions CI/CD — работещ

Workflow-ът `.github/workflows/eas-update.yml` автоматично пуска `eas update --branch preview` при всеки push към `master` (с изключение на промени само в `.md` файлове, виж `paths-ignore`).

**История на проблема (за справка):** Дълго време workflow-ът гърмеше с `exited with non-zero code: 1` на различни стъпки от `eas update`, въпреки валиден `EXPO_TOKEN` (`eas whoami` минаваше успешно) и идентична `eas-cli` версия (20.4.0) с локалната среда. Причината се оказа поредица от три липсващи конфигурационни елемента в repo-то, които не пречеха на локалното изпълнение, защото локалната среда вече ги имаше извън git:

1. **`expo-image-picker`** беше реферирана в `app.json` plugins, но липсваше от `package.json` dependencies → `expo config --json` гърмеше тихо без полезен stack trace.
2. **`eas.json`** изобщо не съществуваше в repo-то (само локално, никога некомитнат) → грешка `EAS project not configured`.
3. **`extra.eas.projectId`** липсваше от `app.json` → същата грешка, докато не се добави (`ce8969c9-88b7-42cb-838f-d3849a88cbcc`).
4. **`expo-document-picker`** (използвана в `DocumentsScreen.js`) също липсваше от `package.json` → Metro bundler гърмеше при export фазата на `eas update`.

Поука: при "работи локално, но не в CI" грешки с Expo/EAS — първо проверявай дали **всички** native пакети, реферирани в код или `app.json` plugins, реално присъстват в `package.json`, и дали `eas.json` + `projectId` са комитнати в git, а не само налични локално.

**Същото важи и за всеки нов пакет, инсталиран с `npx expo install`** — той променя `package.json` и `package-lock.json` локално, но ако тези два файла не се commit-нат, CI билдът гърми с `Unable to resolve module`. Правило: инсталация на пакет и commit на двата файла са една стъпка, не две.

## ⚠️ `main` срещу `master` — работният бранч е `master`

Бранчът по подразбиране в GitHub е `main`, но цялата работа и CI/CD вървят по `master`. Ако `main` остане назад, всеки инструмент, който чете „бранча по подразбиране" (GitHub UI, API заявка без изричен бранч, външен агент), ще види стар код и ще направи грешни изводи.

Точно това се случи на 25 август 2026 — заявка към GitHub API върна версия на `AIPlannerScreen.js` отпреди цяло пренаписване, защото параметърът за бранч беше подаден грешно и мълчаливо се приложи default-ът. Грешката не хвърли изключение, а просто върна друг файл.

`main` е изравнен с `master` на 26 август 2026. При работа занапред: или синхронизирай `main` периодично (`git push origin master:main`), или направи `master` бранч по подразбиране в настройките на repo-то и приключи темата.

## ✅ AI Trip Planner — ключът е сървърно скрит

Anthropic API ключът никога не достига клиентския JS бъндъл (за разлика от React Native env variables, всеки бъндъл е extractable от инсталирано приложение). Вместо това:

- Supabase Edge Function `ai-trip-planner` (project `neorbblppjpxddldjkwn`) приема параметрите на формата и проксира заявката към `api.anthropic.com`, четейки ключа от `Deno.env.get("ANTHROPIC_API_KEY")` — стойност, която живее само в Supabase Edge Function Secrets, никога в git или клиента.
- `AIPlannerScreen.js` вика функцията през `supabase.functions.invoke("ai-trip-planner", { body: {...} })`.
- `verify_jwt: true` на функцията — само логнати потребители на приложението могат да я викат.
- Тествано и потвърдено работещо (30 юни 2026): заявка през Supabase Dashboard test panel върна `200` с реален генериран план.

Ако някога се пренасочи към друг AI providers или се добавят нови AI функции, същият модел (Edge Function + secret) трябва да се използва — никога директен `fetch` от клиента с ключ.

**Модел:** от версия 17 — `claude-sonnet-5`. Смяната е заради географските грешки в маршрутите. Sonnet 5 е $2/$10 за милион токена срещу $1/$5 на Haiku 4.5, тоест около шест цента разлика на план — при положение че осемте уеб търсения сами по себе си струват до осем цента ($10 на 1000 търсения). Тежестта в сметката е търсенето, не моделът.

Тук нарочно стои псевдонимът, а не датирана версия: Anthropic още не са публикували датиран идентификатор за Sonnet 5. Правилото „пълно име вместо псевдоним“ (заради което по-рано се ползваше `claude-haiku-4-5-20251001`) остава в сила и ще се приложи, щом излезе такъв.

**Rotation на Anthropic ключа**: ключът трябва да се обнови на **две места**, инак някоя част ще спре да работи:
1. **Supabase Edge Function Secrets** — за GoTogether AI Planner (Dashboard → Project → Edge Functions → Secrets → `ANTHROPIC_API_KEY`)
2. **Vercel Environment Variables** — за SaveCheck (различен проект, същият ключ)

Локалният `.env` отпадна на 29 август. Приложението не чете нито една променлива от средата — адресът на Supabase и анонимният ключ са записани направо в `lib/supabase.js` (анонимният ключ е публичен по замисъл и е защитен от RLS). Файлът само вкарваше Anthropic ключа в средата на всеки EAS билд без никаква причина.

**Редът при смяна е важен:** нов ключ → смяна в Supabase → проверка с истински план → чак тогава триене на стария. Обратният ред оставя планера мъртъв между стъпките.

След rotation задължително се re-deploy-ва Edge Function-ата (нова версия), защото Supabase може да кешира secrets. Проверка че новият ключ работи: `Invoke-RestMethod` към `api.anthropic.com/v1/messages` с ключа в `x-api-key` header.

## ✅ AI Планер — запазване, история и споделяне

Планът не е еднократен изход на екрана, а запис в таблица `trip_plans` (`trip_id`, `created_by`, `content`, `params` jsonb, `created_at`).

**Автоматично запазване.** Всяко генериране и всяка корекция записва нов ред веднага, без да се чака натискане на „Запази". Причината е конкретна: втори генериран план беше изгубен, защото не беше запазен ръчно. Бутонът „Запази" вика същата функция, но вече е застраховка, не единствен път.

**Версии срещу отделни планове.** Понеже всяка корекция е нов ред, броенето „колко плана има това пътуване" по брой редове дава грешно число — една корекция вдигаше бройката, все едно е нов план. Затова в `params` се пази `planGroupId`: първоначалният план получава ново, а всяка негова корекция наследява същото. Badge-ът на Dashboard брои **уникалните** `planGroupId`, не редовете. По-стари записи отпреди тази промяна нямат `planGroupId` и се броят поотделно — няма как да се свържат ретроактивно.

**ROUTE_META — какво реално е решило AI-то.** Историята показва маршрут (начало → спирки → дестинация), но когато потребителят остави дестинацията празна и AI сам я избере, формата не знае какво е било избрано и редът излизаше без крайна точка. Решението не е да се парсва готовият текст, а протокол между функцията и клиента: промптът инструктира модела да изведе като първи ред

```
[ROUTE_META]start=<НАЧАЛНА ТОЧКА>|dest=<РЕАЛНАТА ДЕСТИНАЦИЯ>[/ROUTE_META]
```

Edge функцията изрязва този ред с regex, преди да върне текста, и подава отделно `meta: { start, dest }`. Клиентът записва стойностите като `resolvedStart` / `resolvedDestination` в `params`. Промптът за корекция също иска редът да се запази или обнови, ако промяната сменя дестинацията. За стари записи без тези полета има резервен етикет — първият смислен ред от текста на плана. Не е перфектен, но е по-добре от празно.

**Форматиране на изхода.** Моделът връща markdown-подобен текст. Той се рендира клиентски в `renderPlanBlocks` — заглавия на раздели, удебелени части, списъци, разделителни линии, натискаеми линкове. Съзнателно е от страната на приложението, а не в промпта: така се подреждат и вече запазените стари планове, без да се пипа Edge функцията. Разпознаването на заглавие е евристично (кратък ред, изцяло с главни букви), за да не се превърне „1. Ден 1: пристигане" в заглавие само защото започва с число.

**Наследяване от пътуването.** Формата се попълва от това, което вече е известно: дестинация, дати и валута от пътуването, брой участници и деца от състава на групата (виж следващата секция). Полетата без друг източник — начална точка, спирки, бюджет, транспорт, тип настаняване, комфорт — се помнят от последния план на това пътуване.

Важно за реда на изпълнение: съставът на групата **винаги** печели пред стойностите от предишен план. Първата версия правеше обратното и на пътуване с вече запазен план промените в „Участници" не се виждаха изобщо — възстановяването от плана се случваше първо и презаписваше изчисленото.

**Споделяне в чата.** Споделя се линк към конкретната запазена версия (`messages.plan_id`), не целият текст — иначе дълъг план задръства чата за всички. Съобщението съдържа маршрута и датите, за да личи кой план е кой, без да се отваря. `ChatScreen` рендира такова съобщение като карта с бутон, който отваря точно тази версия в планера.

## ✅ Състав на групата — възрастни и деца

`trip_members.weight` пази **общия** брой хора, които участникът представя (по него се делят разходите), а `trip_members.children` — колко от тях са деца. Ограничение в базата: `children >= 0 and children <= weight`.

**В интерфейса обаче не се показват тези две числа.** Показват се **Възрастни** и **Деца** — две равностойни числа, които се събират, плюс изчислено „Общо: N души". Причината е четимост: „Общо хора 4 / от които деца 2" се четеше двусмислено — на бърз поглед 4 и 2 изглеждат като 6. Възрастните се смятат като `weight - children`, а при промяна на което и да е от двете се записва новият сбор. Данните в базата не се променят от това решение, само представянето.

Броят деца се ползва от AI планера — самото тегло не носи информация за възраст, затова преди трябваше да се въвежда ръчно при всяко планиране.

**Кой може да променя.** Две RLS политики за UPDATE върху `trip_members`, комбинирани с ИЛИ:
- `trip_members_update` — `auth.uid() = user_id`, всеки променя себе си
- `owner_can_update_members` — организаторът на пътуването променя всекиго

**Капан, който си струва да се помни:** когато RLS откаже UPDATE, Postgres **не връща грешка** — просто не обновява нито един ред. Ако кодът прави оптимистично обновяване на екрана, потребителят вижда нова стойност, която базата не пази, и тя се връща при следващото зареждане. Затова заявката иска обновените редове обратно (`.select()`) и празен резултат се третира като отказ. Същото важи за всяко друго място, където се пише в таблица с RLS.

## ✅ Supabase anon key — хардкоднат в клиента

`lib/supabase.js` **хардкодва** anon key директно като стринг литерал, не чете от `process.env.SUPABASE_ANON_KEY`. Причината: React Native/Expo env variable зареждането не е надеждно — `process.env` в клиентския бъндъл често идва като `undefined`, което води до `Invalid API key` грешки без ясна причина.

**Това е безопасно, защото anon key е публичен по дизайн** — той е защитен от Row Level Security (RLS) политики в базата, не от secrecy. Всеки клиентски JS бъндъл (React Native, web, mobile) така или иначе експонира ключа при runtime.

**Rotation на anon key** (при компрометиране или ротация): смени в `lib/supabase.js`, commit-ни и push-ни към `master` → CI/CD автоматично прави EAS update.

**Различаване от service_role key:** anon key **винаги** започва с `eyJhbGciOiJIUzI1NiIs...` (JWT формат). Ако видиш `sb_secret_...` или `sb_publishable_...` префикс — това **не са** anon/service_role JWT-та (те са Supabase Vault/новия ключов формат, който не се използва тук). Копирай ключа от Dashboard → Project Settings → API → **Project API keys → anon public**.

## ⚠️ Имейл шаблони — всеки сценарий има отделен шаблон

Supabase има **шест отделни шаблона** за различни събития (Dashboard → Authentication → Emails). GoTogether ползва реално само два от тях, но е критично и двата да съдържат `{{ .Token }}`:

| Шаблон | Кога се ползва | Трябва да съдържа |
|---|---|---|
| **Magic link or OTP** | Вход на **съществуващ** потребител | `{{ .Token }}` |
| **Confirm sign up** | Първи вход на **нов** потребител | `{{ .Token }}` |
| Invite user / Change email / Reset password / Reauthentication | Не се ползват от приложението | — |

**Бъгът, който хванахме на 9 август 2026:** шаблонът "Magic link or OTP" беше преведен на български и съдържаше кода, но **"Confirm sign up" беше останал с англоезичния default** — subject "Confirm your email address" и тяло само с `{{ .ConfirmationURL }}` (линк), без никакъв код.

Резултатът: всеки нов потребител получаваше писмо с линк за потвърждение, докато приложението чакаше 6-цифрен код. Нямаше какво да въведе. Съществуващите акаунти (`temelkoh@gmail.com`, `temelkoh@hotmail.com`) работеха безпроблемно, защото за тях се ползва другият шаблон — затова бъгът остана скрит до първия реален външен тестер.

Поука: при промяна на един шаблон, провери и останалите, които реално се използват. Разминаването между subject-а в Resend логовете и очаквания subject е добър индикатор кой шаблон е сработил.

```powershell
Resolve-DnsName -Name _dmarc.wegotogether.xyz -Type TXT -Server 8.8.8.8
Resolve-DnsName -Name send.wegotogether.xyz -Type TXT -Server 8.8.8.8
```

`SERVER_FAILURE` от локалния резолвър не значи липсващ запис — при реална липса се връща `NAME_ERROR` (NXDOMAIN). Затова проверката минава през публичен DNS (`8.8.8.8`).

**Настройки, които подобряват доставяемостта** (всички приложени):
- **DMARC** — `v=DMARC1; p=none;` на `_dmarc` поддомейна. Добавен на 9 август 2026; `p=none` само наблюдава, не блокира.
- **Подател** — `hello@wegotogether.xyz` вместо `noreply@`. Спам филтрите гледат подозрително на `noreply` адреси, особено от нови домейни. Сменя се в Supabase → Authentication → SMTP Settings → Sender email. Адресът не трябва да съществува като реална пощенска кутия.
- **Без външни линкове** — OTP писмото съдържа само текст и код. Разминаване между домейна на подателя и домейни в съдържанието е фишинг сигнал.

Resend показва тези препоръки в таба **Insights** на всяко писмо.

**Диагностика когато писмо „изчезне":** статусът в Resend (`Sent` → `Delivered`, без `bounced`) казва само че приемащият сървър го е приел. Какво става после е извън контрола на подателя. На 9 август писмо до **Google Family Link детски акаунт** беше отчетено като `delivered`, но не се появи нито в inbox, нито в спам — родителският контрол блокира писма от непознати податели напълно. Същият код до обикновен Gmail акаунт пристигна за секунди.

Поредност при диагностика: **1)** провери Supabase auth логовете дали заявката е стигнала и с какъв адрес (там хванахме печатна грешка — `...@gmail.comn`, която даде `bounced`); **2)** провери Resend дали писмото е изпратено и с кой subject (издава кой шаблон е сработил); **3)** отвори Preview да видиш дали кодът реално е в тялото; **4)** тествай с друг имейл адрес, за да разграничиш проблем в конфигурацията от проблем при конкретния получател.

## ⚠️ Тестване с външни потребители — ограничения на Expo Go

Expo Go има фундаментално ограничение за споделяне: **всеки тестер трябва да е логнат в Expo акаунт** (свой или споделен), за да види проекта в "Projects" секцията. Директният линк към EAS update (`expo.dev/accounts/temelko/projects/gotogether/updates/...`) връща **"Account not found"** за други потребители, защото проектът не е публичен.

**Вариантите за тестване с външен приятел (без покупки):**
1. Приятелят си създава безплатен Expo акаунт, ти го добавяш като member в Expo dashboard (Members → Add member) — най-простото, но изисква акаунт.
2. `npx expo start --tunnel` от твоя компютър, приятелят сканира QR кода директно в Expo Go (не с камерата). Работи и в различни мрежи през ngrok tunnel, но само докато твоят компютър е онлайн и Metro върви. Ако `--tunnel` гърми с `Cannot read properties of undefined (reading 'body')` — това е бъг в новите версии на `@expo/ngrok`, workaround е `npm install -g @expo/ngrok@4.1.0`.
3. Google Play Internal Testing ($25 еднократна такса) — генерира `.apk` от `eas build --platform android --profile preview` → тестерът инсталира от линк без Expo Go изобщо. Много по-евтино от Apple ($99/год).
4. TestFlight — изисква Apple Developer акаунт (виж push notifications секцията).

**Ако линкът се отваря в Safari/Chrome вместо в Expo Go**, тестерът трябва да копира линка и да го постави ръчно в Expo Go. От по-новите версии на Expo Go (SDK 54+) опцията "Open from URL" в Settings **е премахната** — единственият надежден начин е през QR код или през Projects list след като е логнат.

**Тестване на две устройства в една мрежа** (най-практичното при разработка): `npx expo start`, натискане на `s` за Expo Go режим, и сканиране на един и същ QR код от двата телефона. На iOS се сканира с камерата, на Android — с четеца вътре в Expo Go. Всяко устройство влиза с различен имейл и се присъединява с invite кода на пътуването. Hotspot от телефон **не работи** — телефонът не може да достъпи Metro сървъра през собствената си точка за достъп.

## ⚠️ Кеширане на Expo Go — как да принудим свеж bundle

Expo Go има **три нива на кеш**, които могат да задържат стар код дори след успешен EAS update:

1. **Metro bundler cache** (компютър): `.expo/` и `node_modules/.cache/` папки → чистене с `npx expo start --clear` или ръчно `Remove-Item -Recurse -Force .expo`.
2. **Bundle cache в Expo Go** (телефон): затваряне на GoTogether от app switcher (**не** back button) → отваряне отново. Понякога това не е достатъчно и трябва пълно преинсталиране на Expo Go.
3. **EAS update cache** (Expo сървъри): не се чисти — просто трябва да се публикува нов update. Ако последният `eas update:list` показва скорошен update, но приложението пак показва стар код, вината е в 1) или 2).

**Диагностика "какво зарежда клиентът в момента":** отвори `http://localhost:8081/lib/supabase.bundle?platform=ios&dev=true` в браузър на компютъра, търси конкретна стойност (напр. anon key префикс) — ако Metro сервира правилния код, но Expo Go пак показва стар — вината е в кеша на телефона.

**Ако Metro пише `No apps connected`** при натискане на `r` (reload) — телефонът изобщо не е свързан към този Metro процес и всичко, което виждаш, идва от кеширан EAS update. Сканирай QR кода наново; появата на нов ред `iOS Bundled` в терминала потвърждава реалната връзка.

**Ако Expo Go гърми с `PlatformConstants could not be found`** — това означава несъответствие между Expo SDK версията в проекта и версията на Expo Go на телефона. Обикновено се случва след `git reset --hard` или ръчна промяна на `package.json`. Решение: `npx expo install --fix` за автоматично привеждане на всички Expo пакети към правилните версии за SDK 54.

## ⚠️ Опасностите на `git reset --hard`

`git reset --hard origin/master` разсинхронизира локалната среда по три начина едновременно:
- **`node_modules/` не се обновява** — старите nested зависимости остават, но `package.json` вече е нов → mismatch.
- **`.env` файлът остава** (в gitignore е), но приложението може да чете различни версии на конфигурация.
- **Пакети инсталирани от EAS runtime (напр. `expo-updates`, `expo-clipboard`)** — CI workflow-ът ги инсталира при всеки build, но локално те са само в `node_modules/`, не в `package.json`. Reset връща `package.json` без тях и всичко гърми.

**След `git reset --hard` винаги пусни:** `npm install && npx expo install --fix` за да синхронизираш локалната среда с новото състояние на `package.json`.

**Внимание — reset може тихо да върне вече направени промени.** На 8 август 2026 се оказа, че `BGN` е обратно във валутните списъци на `TripSetupScreen.js`, въпреки че беше премахнат в Ден 8; промяната е била изгубена при reset/force push по време на маратона. Поука: след reset или force push си струва да се провери дали конкретни скорошни промени наистина са оцелели, а не да се допуска, че историята е чиста.

## ✅ Safe area — iOS notch и Android navigation bar

Всички екрани четат реалните отстояния през `useSafeAreaInsets()` от `react-native-safe-area-context`, вместо хардкоднати `paddingTop: 60`, калибрирани за iPhone.

**Проблемът, който решихме (8 август 2026):** на Android навигационната лента (трите бутона или жестовата чертичка) застъпваше долните елементи. В чата това беше блокиращо — полето за писане беше точно под лентата, така че тапването задействаше системните бутони вместо input-а. Хардкоднатите стойности бяха невидим проблем и отгоре: status bar-ът на Android има различна височина от iPhone notch-а.

**Реализация:**
- `App.js` обвива всичко в `<SafeAreaProvider>` — без него `useSafeAreaInsets()` връща нули.
- Всеки екран взима `const insets = useSafeAreaInsets()` и ги прилага като `contentContainerStyle={[styles.scroll, { paddingTop: insets.top + 20, paddingBottom: insets.bottom + 40 }]}`.
- Базовите стилове съдържат само хоризонталния `padding`; вертикалните отстояния идват изцяло от insets.
- `ChatScreen.js` прилага `insets.bottom` върху `inputRow` и `editBar` (не върху контейнера), защото полето за писане е фиксирано долу, извън скролируемата зона.

**Защо този пакет, а не ръчна кръпка:** `StatusBar.currentHeight` дава само горната височина на Android и нищо за навигационната лента, а фиксирано число (напр. `paddingBottom: 24`) е грешно на устройства с жестова навигация. `react-native-safe-area-context` е официално препоръчан от Expo и **вече вграден в Expo Go**, така че не изисква нов development build — рискът от CI проблем е само в това да се забрави commit на `package.json`.

## ✅ Връщане на премахнат участник — само с уредени сметки

Когато организаторът премахне участник, неговите минали `expense_splits` записи остават в базата непокътнати (не се трият) — стар дълг е реален и трябва да бъде уреден, не изтрит. Организаторът вече може да потвърди settle вместо напусналия участник (виж "Управление на участници" по-долу).

**Проблем, който решихме (30 юни 2026):** ако организаторът деблокира участник, докато той все още има неуредени сметки, тези стари дългове автоматично се връщат в активните изчисления на `ExpensesScreen` при повторното му присъединяване — независимо дали той реално е участвал в нещо ново. Тъй като в повечето случаи премахнат участник не се връща, а организаторът вече settle-ва вместо него, по-логично е деблокирането да изисква чисти сметки, вместо да добавяме нова "замразяване/съживяване" логика.

**Решение:** `handleUnblock` в `DashboardScreen.js` сега проверява и двете посоки на дълга, преди да позволи деблокиране:
- Дължи ли участникът пари по неуредени `expense_splits` (той е участник, не платец)
- Дължат ли му пари по разходи, които той е платил, с неуредени splits от други

Ако има неуредена сума в която и да е посока, деблокирането се отказва с конкретно съобщение колко лева и в коя посока пречат. Организаторът трябва първо да уреди сметките през Разходи → Как да се изравним (потвърждавайки вместо напусналия, ако той не може лично), и чак тогава да деблокира — гарантирано чист старт без наследени задължения.

## ✅ Многовалутни разходи — EUR база с реални курсове

Разходите се въвеждат в реалната валута, в която са направени (не само в една обща валута), а изравняването показва общата сума в EUR база плюс местната валута на пътуването, ако е различна.

**Архитектура:**

- **DB**: `expenses.currency` + `trips.local_currency` (default `EUR`, избираема при създаване и при редакция на пътуването измежду EUR/USD/GBP/CHF).
- **Курсове**: Supabase Edge Function `currency-rates` проксира [Frankfurter](https://frankfurter.dev) (ECB референтни курсове, безплатна, без API ключ, ~30 активни валути) и пълния ISO списък с имена (`/v1/currencies`), с 6-часов in-memory кеш — ECB публикува веднъж дневно, така че няма нужда от по-чести заявки.
- **Въвеждане на разход** (`ExpensesScreen.js`): избирател на валута — chip-ове за чести валути (EUR, USD, GBP, CHF) + търсене в пълния списък от Frankfurter за всичко останало. По подразбиране **EUR**.
- **Изчисления**: `calcSettlements` конвертира всеки `expense_split` в EUR преди баланс смятането (`toEUR()` помощна функция), така че разходи в различни валути в едно пътуване се сумират коректно. Обобщенията ("Общо", "Ти дължиш", "Дължат ти") са винаги в EUR.
- **Показване в "Как да се изравним"**: всяка сума се показва двойно — EUR (основна) + местната валута на пътуването (ако е различна от EUR), малко под нея.
- Ако курс липсва, кодът показва суровата сума без конверсия вместо да гръмне — graceful degradation.

**Важно — валута без ECB курс дава тихо грешни изравнявания.** България е приела еврото в текущия сценарий, затова **BGN не присъства** в активния ECB feed на Frankfurter. Понеже `toEUR()` връща сумата непроменена, когато няма курс, разход от 100 BGN се третираше като 100 EUR — сметките изглеждаха коректни, но бяха двойно завишени. Затова BGN е премахнат от всички валутни списъци (заменен с CHF), а съществуващите записи в базата са мигрирани на EUR. Същото важи за всяка бъдеща валута, която отпадне от ECB feed-а.

## ✅ Дати на пътуването

`trips.start_date` и `trips.end_date` (nullable `date` колони, по избор) се задават с календарен избор (`components/DatePicker.js`) — при създаване в `TripSetupScreen.js` и при редакция от организатора в `DashboardScreen.js`. DatePicker е написан на чист JS (месечен grid, български имена на месеци и дни, `minDate` за крайната дата), за да не въвеждаме native dependency.

`DashboardScreen.js` показва диапазона в trip card (формат ДД.ММ.ГГГГ) плюс статус badge, изчислен спрямо днешна дата: "🟢 В момента", "Утре", "След 12 дни", "Приключи преди 3 дни". Същата функция (`computeTripStatus`) дава и `sortOrder` за подредбата в trip picker-а: активни → предстоящи (най-скорошните първо) → без дати → минали (приглушени в сиво).

**Кой месец отваря календарът.** При избор на крайна дата календарът трябва да отвори месеца на вече избраната начална дата, а не текущия — иначе при пътуване след няколко месеца трябва да превърташ ръчно всеки път. Две поуки от решаването на този дребен на пръв поглед проблем:

1. **Синхронно, не през `useEffect`.** Първата версия слагаше ефект, зависещ от `visible`, който коригираше месеца при отваряне. Не работеше надеждно — модалът успяваше да се покаже с грешния месец. Изчислението и `setVisible(true)` вече се случват в един и същ обработчик на натискане, така че няма кадър с грешно състояние.
2. **Истинската причина беше другаде.** Дори след поправката календарът пак отваряше грешния месец — защото формата на планера се предзарежда с датите на самото пътуване, включително крайната. Тя не беше празна, а стара, и календарът честно показваше нейния месец. Решението е при промяна на началната дата крайната да се нулира.

### Ден 10 — 25-26 август 2026 — AI Планерът става част от приложението
Дотук планерът беше по-скоро демо: генерираше текст, който живееше само на екрана. Този ден го превърна в нещо, което групата реално ползва — планове, които се пазят, намират се и се споделят.

**Запазване и история:**
- Всяко генериране и всяка корекция се записват автоматично в `trip_plans` — поводът беше реално изгубен втори план, който не беше запазен ръчно.
- История на плановете, подредена хронологично, с **маршрут** като етикет вместо час на запазване — по маршрут се разпознава кой план кой е.
- Споделяне в чата като линк към конкретната версия (`messages.plan_id`) + карта с бутон в `ChatScreen`, вместо копиране на целия текст. Текстът на съобщението включва маршрута и датите, за да личи кой план е споделен.

**ROUTE_META — протокол вместо парсване:**
- Когато потребителят остави дестинацията празна и AI сам избере къде да се пътува, историята нямаше откъде да знае резултата и редът излизаше без крайна точка. Вместо да се парсва готовият текст, промптът вече иска машинно четим първи ред `[ROUTE_META]start=...|dest=...[/ROUTE_META]`, който Edge функцията изрязва и връща отделно като `meta` (версия 15). Клиентът го пази в `params` като `resolvedStart`/`resolvedDestination`. Виж секцията "AI Планер — запазване, история и споделяне".

**Форматиране на изхода:**
- Планът се показваше като стена от текст с видими markdown маркери (`**`, `##`, `---`). Добавен клиентски рендер — заглавия на раздели, удебелени части, списъци, разделителни линии, натискаеми линкове. Клиентски, за да се подредят и вече запазените стари планове.

**Формата наследява каквото приложението вече знае:**
- Дестинация, дати и валута от пътуването; брой участници и деца от състава на групата; останалите полета се помнят от последния план на това пътуване.
- **Бъг с реда на изпълнение:** първата версия оставяше възстановяването от предишния план да презапише изчисленото от участниците, така че на пътуване с вече запазен план промените в „Участници" не се виждаха изобщо. Изглеждаше като „работи само за нови пътувания". Съставът на групата вече винаги печели.

**Състав на групата — нова колонка `children`:**
- `weight` знаеше колко души представя участник, но не и на каква възраст, затова планерът питаше за брой деца ръчно. Добавена колонка `children` с ограничение `children <= weight`.
- В интерфейса се показват **Възрастни** и **Деца** като две събиращи се числа плюс изчислено „Общо" — първата версия („Общо хора / от които деца") се четеше двусмислено, 4 и 2 изглеждаха като 6.
- **Права:** дотогава само самият участник можеше да променя своя ред — организаторът не можеше да коригира никого. Добавена политика `owner_can_update_members`.
- **Капан:** отказ от RLS не хвърля грешка, а просто не обновява ред. Оптимистичното обновяване на екрана показваше стойност, която базата не пазеше, и тя се връщаше при следващо отваряне. Заявката вече иска обновените редове обратно и празен резултат се третира като отказ. Виж секцията "Състав на групата".

**Dashboard:**

участници**.

Решението е профил-надгробен камък: `profiles_id_fkey` отпада, профилът остава
анонимизиран, за да не увиснат общите сметки, а `auth.users` редът се трие
изцяло. Организаторството на пътуване с други участници минава автоматично към
присъединилия се пръв след теб; пътуване с един участник се трие изцяло.

**Вход за ревюърите** (Edge функция `review-signin`):
Влизането е с код по имейл, а ревюърите на двата магазина нямат достъп до
чужда поща — тоест виждат празен екран и отхвърлят приложението. Първият план
беше истинска пощенска кутия на домейна, но страницата на Spaceship за купуване
дава 404 и от домашна мрежа, и от мобилни данни.

Затова един-единствен адрес приема фиксиран код, описан в бележките за ревю
(тоест не е скрита функционалност, а обикновен демо акаунт). Кодът живее само в
Edge функцията и го няма в бандъла; функцията има вградена дата на изтичане, за
да не остане да виси, ако я забравим. Акаунтът е напълнен с правдоподобно
пътуване — трима участници, девет души, пет разхода в две валути, чат и
примерен ваучер.

**Документите вече не са публични.** Кофата в Storage беше `public`, а
политиките ѝ бяха `allow_all_read`, `allow_all_upload` и `allow_all_delete` за
роля `public` — тоест с публичния ключ на приложението всеки можеше да чете,
качва и **трие** чужди файлове. Сега кофата е частна, трите политики са
заменени с проверка по членство (първата папка в пътя е `trip_id`), а
приложението иска подписана връзка за пет минути при всяко отваряне. В базата се
пази пътят, не URL. Има и таван от 25 MB на самата кофа, не само в интерфейса.

**Сигурност в базата:**
- `get_my_trip_ids` и `handle_new_user` са `SECURITY DEFINER` без фиксиран `search_path` — класическият път за повишаване на права. Заковани на празен път, с пълни имена на схемите в телата. `get_my_trip_ids` стои в **13** RLS политики, така че двете промени задължително вървят заедно
- `handle_new_user` вече не е достъпна като `/rest/v1/rpc/`. Отнемането на права от `anon` и `authenticated` не стига — те наследяват през `PUBLIC`

**Лимит на AI планера** (таблица `ai_usage`):
Дотук планерът нямаше никакво ограничение. Три тавана: 3 нови плана и 10
корекции на месец на потребител, 12 заявки за денонощие, и 300 за цялото
приложение като аварийна спирачка. Броенето е по редове в дневник, не по брояч
в колона — така две едновременни заявки не се надпреварват. Записва се едва
след успешен отговор, за да не се губи квота за нещо, което не е получено.

Корекциите отначало не се брояха изобщо, с довода че поправянето на собствен
план не бива да плаши човека. Тестът показа дупката: в полето за корекция може
да се напише „направи го за Париж вместо Рим" и отговорът е на практика нов
план. Тоест месечните три се заобикаляха с едно изречение.

Отказът се връща със статус **200**, а не 429 — `supabase-js` подменя тялото на
всеки не-2xx отговор с „Edge Function returned a non-2xx status code", тоест при
429 човекът щеше да види техническа безсмислица вместо причината.

**Дребни поправки от истинска употреба:**
- Поканата тръгваше без тема и съветваше да се инсталира Expo Go. Заглавието трябва да се подаде на две места — Android го чете от `content.title`, iOS слага темата от `options.subject`
- Аватарите в чата бяха с един цвят, зашит в стила. Сега цветът се избира по `user_id` от палитра, не по позиция в списъка, за да не скачат при зареждане на стари съобщения
- Документите отваряха всичко с `Linking.openURL` и телефонът решаваше кое приложение да поеме връзката. Сега снимките се отварят вътре в приложението, а PDF отива в таб върху него през `expo-web-browser`, зареден лениво през `require` в `try/catch`, за да не гърми върху билд без нативния модул
- Списъкът с участници подскачаше при всяка промяна на брояч, защото заявката нямаше `ORDER BY`, а редът се пренаписва при UPDATE. Организаторът е пръв, останалите по реда на присъединяване

**Първи истински билд** (`preview`, вътрешно разпространение): APK с линк и QR
от expo.dev, без Google Play Console. Първият билд, който носи
`expo-web-browser`, изчистените Android разрешения и
`ITSAppUsesNonExemptEncryption`.

**Урок за работата с помощни агенти:** качването на версия 18 мина през агент,
който се спъна в лимит по средата. Функцията се качи правилно, но при
преписването една дума в промпта се смени. Отделно докладът за проверката беше
изкривен — „Северна Македония" беше преписано като „Събора Македония", при
положение че в нито един файл нямаше такова нещо. Изводът: текст, минал през
езиков модел, не е доказателство. Проверката се прави с `diff` и `md5sum`,
не с преразказ.

### Ден 12 — 31 август – 1 септември 2026 — известия и дребните неща от истинската употреба

Денят тръгна от бележките на приятелите, които вече ползват приложението, и
свърши с нов билд.

**Кликаеми линкове в чата.** Съобщението се рисуваше като обикновен `Text`, а
обикновеният текст в React Native не разпознава адреси — нито грешка, нито
предупреждение, просто нищо. Текстът вече се нарязва на парчета и адресите
стават натискаеми. Крайната пунктуация се отрязва: „виж
https://maps.app.goo.gl/abc." отваря адреса без точката. Голи домейни като
`booking.com` нарочно **не** се хващат — по-добре един линк да остане текст,
отколкото половин изречение да посинее и да води наникъде.

Картовите адреси (Google Maps, Apple Maps, Waze) се подават на системата, за
да ги поеме приложението за карти — вътрешният браузър би показал уеб
версията и би загубил навигацията. Всичко останало се отваря вътре в
приложението.

**Увеличаване на снимки в документите.** Написано на `PanResponder` и
`Animated`, тоест само с това, което React Native носи. Библиотека за жестове
би значела нативен модул, нов билд и нов линк за всички — а поправката така
пътува като обикновен ъпдейт. Щипване с два пръста до 4×, местене с един,
двойно тапване за 2.5×, автоматично връщане под 1×.

**Бутон „към последното съобщение" в чата** — и една поправка, която не беше
поискана. Списъкът се смъкваше до дъното при *всяко* ново съобщение, тоест
четенето на стар разговор се прекъсваше от всеки, който пише. Сега това става
само ако човекът вече е долу.

**Известията** — виж секцията по-горе. Ден работа, от която най-дългата част
беше Firebase и EAS credentials, а не кодът.

**Изненадата на деня беше извън кода.** Балансът в Anthropic беше паднал до
**$0.04** — юнският кредит от $6 беше изразходван и планерът беше на часове от
това да спре, при това точно преди раздаването на линка на приятели.
Заредени $20, таван на разхода $50 (по подразбиране беше $200 000, стойност
проектирана за компании) и известие при $20. Проверката на картата се
провали, защото запазената карта беше изтекла — смени се с нова.

Поука: безплатните кредити свършват тихо. Единственият сигнал беше, че
приложението започва да връща грешка при генериране на план.

### Ден 13 — 2 септември 2026 — какво има наоколо, снимки в чата и три грешни диагнози

Най-дългият ден дотук и най-полезният, защото всичко в него дойде от реална
употреба, а не от списък с идеи.

**„Какво има наоколо" — от бутон до инструмент.** Тръгна като един линк към
картите с думата „забележителности". После се оказа, че трябват и заведения; после
че фиксираните категории не стигат; после че шест категории затрупват екрана над
плана. Крайният вид: свит ред, който се отваря при нужда, шест бързи категории,
свободно текстово поле (пишеш „веган", „рент а кар", „пералня"), местата от плана
като бутони, плюс „📍 Около мен" и поле за място извън плана.

Ключово решение: **това е линк, не наша функция.** Не струва нищо, не влиза в
никаква квота и показва снимки, оценки и работно време, каквито ние никога няма
да имаме. Подреждане по рейтинг обаче не контролираме — универсалният адрес на
картите не приема такъв параметър.

**„Около мен" отне три опита.** Първо подадохме търсене без място, вярвайки, че
картите ще центрират по телефона — те центрират по последното, което са
показвали, тоест по дестинацията. После пробвахме `geo:0,0?q=…` на Android —
пак картите решаваха. Чак `expo-location` с истински координати и адрес от вида
`/@широчина,дължина,13z` даде еднакво поведение за всяка дума. Отделно се оказа,
че на телефона на разработчика **разрешението за местоположение на самите Google
Maps е било изключено** — оттам липсваше синята точка, което няма нищо общо с
нашия код.

**Споделяне отвън в чата.** Приложението се регистрира като приемник на Android:
от картите, браузъра или където и да е → Сподели → GoTogether → избираш пътуване
→ линкът влиза в чата. Първият опит за инсталация се провали, защото
`npx expo install` знае съвместимите версии само за пакетите в списъка на Expo, а
този е външен — дръпна последната (8.0.1, за SDK 57) и билдът гръмна. За SDK 54
линията е 5.x.

**Снимки в чата.** Камера или галерия, до 10 наведнъж, подпис по желание,
прелистване настрани при разглеждане, запазване в галерията, две нива на
качество. Хранилището не се пипна изобщо: снимките отиват в папката на
пътуването, където правилата за достъп вече казват „само членове", в подпапка
`chat/`, а Документите се изброяват от таблица, не от папката. В базата влезе
една колона — `image_path` в `messages`.

Смаляването мина през своя грешка: първата версия компресираше **два пъти** —
веднъж при избора, веднъж при смаляването — тоест второто минаване тръгваше от
вече развалена снимка. Сега е едно минаване: 2048 px при обикновено качество,
3200 px при високо. Изборът на качество се предлага наново при всяко изпращане,
защото „високо" е решение за конкретната снимка, а не режим, в който човек
забравя, че е.

**Три грешни диагнози за едно и също.** На iOS снимката не се затваряше. Първо
реших, че бутонът е под изреза — преместих го. После, че вътре в `Modal` хукът за
безопасната зона връща нули — сложих ленти долу. После, че трансформираната
снимка се рисува върху бутоните и им яде допира — добавих изрична дълбочина и
тапване по снимката като втори изход.

Истинската причина беше друга: **прозорецът се затваряше и се отваряше сам.**
Лентата със снимки следи прелистването и при изчезването на прозореца iOS
изстрелва още едно събитие за спряло движение; то пресмятa „снимка 0" и я
записва обратно. Поправката е три реда — изход, ако вече няма отворена снимка.

Поуката е за метода, не за кода: след втората грешна хипотеза трябваше да спра да
предлагам поправки и да поискам един разграничаващ признак (проблясва ли бутонът
при натискане), който щеше да раздели „допирът не стига" от „състоянието не се
задържа". Три опита на сляпо струваха повече от един въпрос.

**Търсене в чата.** Оказа се най-евтиното от всичко: съобщенията и без това са в
паметта, значи търсенето е филтър, не заявка. Работи и без мрежа. Тапване по
резултат връща в разговора на точното място, със светване за две секунди.
Ограничението е известно — четат се до 1000 съобщения на пътуване.

**Сигурност.** GitHub вдигна аларма за „Google API Key" в `google-services.json`.
Файлът е публичен по замисъл — пътува вътре във всеки APK. Ключът беше ограничен
по приложение (пакет + SHA-1), което е истинската защита; ограничението по API
беше нарочно пропуснато, защото грешен избор там спира издаването на push токени
за нови инсталации, а печалбата е нулева при вече затворена врата.

## 🔨 Преди следващия билд — не се минава с `eas update`

Тези неща изискват **нов нативен билд**. OTA обновление не ги внася, защото
липсва нативният код в binary-то.

✅ `expo-web-browser` и `ITSAppUsesNonExemptEncryption` влязоха с билда от
29 август. ✅ `expo-notifications` и изравняването на версиите (`expo` 54.0.37,
`expo-constants` 18.0.14, `expo-updates` 29.0.20) влязоха с билда от
1 септември. ✅ `expo-location` и `expo-share-intent` влязоха с билда от
2 септември; ✅ `expo-media-library`, `expo-file-system` и
`expo-image-manipulator` — със следващия същия ден. Остава:

- **Не пипай `version` в `app.json`** — `runtimeVersion` е вързан за него
  (`policy: appVersion`). Вдигането му спира обновленията по въздуха към вече
  раздадените билдове.
